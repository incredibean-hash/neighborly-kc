# Neighborly KC — bug fix pass (Aug 17, 2026)

Focus: intermittent first-attempt sign-in failures, Messages (DMs), and Profiles.
Verified with a clean `next build` (all 17 routes compile, no type errors).

---

## 1. Sign-in failing on the first attempt — root cause found

**The bug.** The Supabase client was created with `detectSessionInUrl: true`
(`lib/community.ts`) *and* `app/page.tsx` also called
`supabase.auth.exchangeCodeForSession(code)` by hand.

A PKCE authorization code and its verifier can only be redeemed **once**. Both
paths raced for the same one-time verifier. Whichever lost threw
`invalid request: both auth code and code verifier should be non-empty`, the
session never landed, and the user was bounced back to the feed still signed
out. On the second attempt the code was fresh again — hence "works the second
time."

**The fix.**

- `detectSessionInUrl` is now `false`. The explicit exchange in `app/page.tsx`
  is the single owner of the code.
- The exchange is guarded by a module-scope `oauthCodeExchangeStarted` flag.
  React Strict Mode mounts effects twice, so the effect itself could redeem the
  code twice on a single page load.
- Before redeeming, the code now checks whether a session already exists and
  skips the exchange if so.
- If the exchange fails *and* no session exists, the sign-in sheet reopens with
  a clear message instead of failing silently.
- Added handling for implicit-flow tokens arriving in the URL hash
  (`#access_token` / `#refresh_token`), which `detectSessionInUrl: false` would
  otherwise ignore for older Supabase email templates.

**Deleted `lib/supabase.ts`.** It created a *second* `createClient` with a
different auth storage key than `lib/community.ts`. It was unused today, but two
GoTrueClient instances in one tab fight over the same session and are a
guaranteed source of random sign-outs the moment anything imports it.

## 2. Messages (DMs)

| Problem | Fix |
| --- | --- |
| Incoming messages never appeared live; you had to refresh. Realtime enforces RLS using the **socket** JWT, and `supabase.realtime.setAuth()` was never called, so the RLS-protected `dms` table delivered zero change events. | Added `authorizeRealtime()` in `lib/community.ts` and call it before subscribing. Also re-applies the token on `onAuthStateChange` so long sessions do not go quiet. |
| The realtime channel was torn down and recreated on **every** conversation switch (`[me, selected]` deps), regularly dropping messages mid-handshake. | Subscribe once per signed-in user (`[me]`) and read the active conversation through a `selectedRef`. |
| Messages arriving for a non-active conversation were discarded entirely. | They now increment an unread count and show a badge in the neighbor list. |
| New messages did not scroll into view. | Added a scroll anchor that keeps the newest message visible. |
| Send errors showed a raw browser `alert()`; RLS rejections were unreadable. | Errors render inline, with a plain-English hint when RLS blocks the insert. |
| Enter sent the message even while a send was in flight (duplicate sends), and Shift+Enter was impossible. | Guarded on `sending`; Shift+Enter no longer sends. |
| Opening `/dms?user=<id>` for a neighbor missing from the sidebar list showed the conversation header as "Neighbor". | That profile is now fetched individually and prepended to the list. |

## 3. Profiles

**`app/profile/[id]/page.tsx`**

- **Editing your own profile could fail outright.** The save ran
  `.update(...).eq('auth_user_id', ...).single()`. For legacy rows where
  `auth_user_id` was never backfilled, that matched **zero rows** and `.single()`
  threw — the user saw "Could not save profile." Now it updates by the profile
  row's own primary key (`p.id`) and reads the row back separately, so a
  restrictive SELECT policy cannot make a successful save look like a failure.
- **The Connect button silently reset.** The connection lookup used
  `.maybeSingle()` on an `.or()` filter, which throws when duplicate legacy rows
  exist in either direction. Changed to `.limit(1)`.
- Pressing Connect when a request already existed surfaced a raw duplicate-key
  error; that case is now handled quietly.

**`app/profile/page.tsx`**

- The page read the theme straight from `localStorage` instead of using the
  shared `useAppTheme()` hook, so it could render in a different theme from the
  rest of the app. Now uses the shared hook.
- A base64 image preview (`data:...`) could be written into `profiles.avatar_url`
  if the save path ran without the upload. Data URLs are now blocked from
  reaching the database.

## 4. Consistency and performance (all pages)

- Every page previously used `supabase.auth.getUser()`, a **network** call, to
  decide whether you are signed in. A slow or failed request made an
  authenticated user see "Sign in to continue." All pages now use
  `getSession()`, which reads the persisted session locally.
  (`/dms`, `/profile`, `/profile/[id]`, `/people`, `/connections`,
  `/notifications`)
- The feed's focus listener captured a stale `posts` closure, so
  `posts.length === 0` was always true and **every window focus reloaded the
  entire feed**. Fixed with a ref.
- An empty feed retried 4 more times with backoff on every load, hammering
  Supabase for brand new neighborhoods. Reduced to a single retry.
